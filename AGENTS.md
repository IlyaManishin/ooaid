# AGENTS.md — правила работы агента над TrackFit

Ты автономный разработчик Android-приложения **TrackFit**. Этот файл — твой операционный регламент. Подробности: `docs/TZ.md` (что строить), `docs/ARCHITECTURE.md` (как строить), `docs/UI_MAP.md` (экраны), `docs/DECISIONS.md` (принятые решения), `docs/SETUP.md` (окружение).

Язык: документация и пользовательские строки — русский; код, идентификаторы, комментарии, сообщения коммитов — английский.

---

## 1. Источники истины и приоритет

При противоречии выше стоит тот источник, что в списке раньше:

1. Прямые указания владельца проекта в текущем задании.
2. `docs/DECISIONS.md` — решения, которыми противоречия уже разрешены.
3. `docs/trackfit.md` — **бизнес-логика** (правила циклов, статусов, уведомлений, тренера).
4. `docs/UI.drawio` (+ `docs/UI_MAP.md`, `docs/ui-dump/UI.dump.txt`) — **экраны, навигация, тексты, раскладка**.
5. `docs/TZ.md`, `docs/ARCHITECTURE.md`.

Правило при конфликте логики между макетом и `trackfit.md`: побеждает `trackfit.md`; конфликт обязательно фиксируется в `DECISIONS.md`. Конфликт по внешнему виду/навигации: побеждает макет.

## 2. С чего начать (bootstrap)

1. Прочитай целиком `docs/TZ.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/UI_MAP.md`, `docs/trackfit.md`.
2. Проверь окружение по `docs/SETUP.md` (JDK, Android SDK, Gradle). SDK на машине владельца **нет**. Если ты можешь выполнить установку из своей среды — выполни. Если нет (нет сети/прав) — **не имитируй сборку**: остановись на задачах, не требующих сборки (написание `:domain` кода и тестов тоже требует Gradle, поэтому остановись полностью), запиши блокер в `docs/QUESTIONS.md` и сообщи владельцу, какие команды из `SETUP.md` ему выполнить.
3. Работай по майлстоунам из `docs/TZ.md` §9 строго по порядку.

## 3. Архитектурные инварианты (нарушать нельзя)

Полное описание — в `docs/ARCHITECTURE.md`. Кратко:

- Три Gradle-модуля: `:domain` (чистый Kotlin/JVM, **ноль** Android-зависимостей) → `:infra` (Room, DataStore, AlarmManager, уведомления, assets) → `:app` (Compose UI, ViewModel, DI, навигация). Зависимости только в эту сторону: `app → infra → domain`, `app → domain`.
- Бизнес-логика живёт **только** в `:domain`. Composable-функции и ViewModel не содержат правил (статусы, циклы, дедлайны, валидация, выбор реплик).
- Время не читается напрямую (`Instant.now()`, `System.currentTimeMillis()`, `LocalDate.now()` запрещены вне одной реализации `TimeSource`). Всё, что зависит от времени, — детерминированные функции от `(state, now, zone)`.
- Состояние производно от сохранённых фактов и часов, а **не** от работающих таймеров/сервисов. Любая команда сначала делает `reconcile(now)`.
- Все изменения состояния — через контроллеры, один писатель (Mutex), одна транзакция на команду.
- Тренер — расширяемая data-driven подсистема (правила + банки фраз), а не `if/else` в UI.
- Все пользовательские строки — в `strings.xml`. Никаких захардкоженных строк в коде/Composable.

Архитектурные ограничения проверяются автоматически (`docs/ARCHITECTURE.md` §15). Падающий `checkArchitecture` = задача не выполнена.

## 4. Git-процесс

- `main` — защищён. **Никогда** не пушь в `main`, не мержи в `main`, не делай force-push куда-либо.
- `develop` — интеграционная ветка. Создай её от `main` в начале работы.
- Рабочая ветка на каждую задачу/подзадачу майлстоуна: `feat/<milestone>-<slug>`, `fix/<slug>`, `chore/<slug>`, `docs/<slug>`. Создаётся от `develop`.
- В `develop` ты мержишь **сам**, когда выполнены условия §7 (Definition of Done). Способ: squash-merge ветки (один коммит на ветку в `develop`) либо fast-forward, если в ветке уже 1–3 осмысленных коммита.
- По завершении майлстоуна открой **Pull Request `develop → main`** (через `gh pr create`, если доступен; иначе сохрани текст PR в `docs/pr/<milestone>.md` и сообщи владельцу). Мерж PR делает только владелец. До его мержа продолжай следующий майлстоун от `develop`, но не трогай `main`.
- В PR: что сделано, какие решения добавлены в `DECISIONS.md`, какие вопросы открыты, как проверить вручную, результат гейта (§7).

## 5. Коммиты

- **Крупные, осмысленные коммиты**: один коммит = один завершённый логический блок (например, «domain: program model + validation + tests»), а не шаг правки. Ориентир: 1–4 коммита на ветку, ≤ ~15 коммитов на майлстоун.
- Запрещены коммиты вида `wip`, `fix typo`, `address review`, цепочки fixup. Перед мержем в `develop` схлопни мусор (`git rebase -i`/`--autosquash` в своей ветке или squash-merge).
- Каждый коммит собирается и проходит тесты затронутых модулей.
- Формат: Conventional Commits — `feat(domain): ...`, `feat(app): ...`, `fix(infra): ...`, `test(domain): ...`, `docs: ...`, `chore(build): ...`. В теле коммита — 2–6 строк «что и зачем», ссылки на ID решений (`D-xx`).
- Не коммить: `local.properties`, `.gradle/`, `build/`, `*.keystore`, IDE-файлы (кроме `.idea/codeStyles` по желанию), SDK, секреты.

## 6. Работа при неполном ТЗ (баланс: не стопориться и не выдумывать)

ТЗ намеренно не покрывает всё. Для каждого пробела классифицируй:

| Тип пробела | Что делать |
|---|---|
| **A. Структурный** (влияет на доменные инварианты, публичные интерфейсы, формат хранения) | Выбери самый простой вариант, согласованный с `trackfit.md`. Запиши в `DECISIONS.md` (ID, варианты, выбор, цена отката), статус `ПОДТВЕРДИТЬ`. Иди дальше. |
| **B. Презентационный** (отступы, иконки, порядок полей) | Следуй макету; если макета нет — стандартные компоненты Material 3. В `DECISIONS.md` не пиши. |
| **C. Новая функциональность, которой нет в ТЗ** | **Не реализуй.** Если без неё ломается сквозной сценарий — минимальная заглушка + пометка `Stubbed` в `DECISIONS.md`. |
| **D. Противоречие источников** | Применить приоритет §1, зафиксировать в `DECISIONS.md`. |
| **E. Блокер** (нет доступа, сети, нужен ассет/контент/решение владельца, без которого нельзя двигаться) | Запиши в `docs/QUESTIONS.md` (вопрос, контекст, твой вариант по умолчанию), продолжи **независимые** задачи. Не останавливай всю работу из-за мелочи. |

Запреты на самодеятельность: никакого бэкенда/сети/аккаунтов/аналитики/рекламы, генеративного ИИ, облачной синхронизации, экспорта/импорта, виджетов рабочего стола, тёмной темы «на всякий случай», дополнительных экранов, настроек и «полезных» фич, которых нет в `trackfit.md`/макете. Не рефакторь работающий код ради вкуса. Не добавляй зависимости без необходимости (каждая — строка в `DECISIONS.md` с обоснованием).

Контент (фразы тренеров, био, фото) — **плейсхолдеры** с пометкой `TODO(content)`. По 3–5 коротких фраз на каждый ключ. Не сочиняй большие объёмы текста.

## 7. Definition of Done (гейт перед мержем в `develop`)

Все пункты обязательны:

1. `./gradlew checkArchitecture :domain:test :infra:testDebugUnitTest :app:testDebugUnitTest :app:lintDebug :app:assembleDebug` — зелёный (на Windows `gradlew.bat`).
2. Для новой доменной логики есть юнит-тесты (граничные случаи времени — обязательно, см. `ARCHITECTURE.md` §14). Тест пишется вместе с кодом, в том же коммите.
3. Нет захардкоженных строк, нет `TODO` без метки (`TODO(content)` / `TODO(ui)` / `TODO(decision D-xx)`).
4. `DECISIONS.md` и `UI_MAP.md` актуальны. Новые решения типа A добавлены.
5. Приложение запускается на эмуляторе/устройстве, если оно доступно; иначе явно напиши в PR «ручная проверка не выполнена: нет эмулятора».

## 8. Версии и зависимости

Версии AGP, Kotlin, Compose BOM, Room, Hilt, Navigation, WorkManager/AlarmManager API и т. д. **не запоминай по памяти** — выбери актуальные стабильные (не alpha/beta/rc) на момент работы, проверь совместимость (таблица AGP↔Gradle↔Kotlin↔JDK в официальной документации), зафиксируй в `gradle/libs.versions.toml` и опиши выбор в `DECISIONS.md`. `compileSdk`/`targetSdk` — последний стабильный API, доступный через `sdkmanager`; `minSdk = 26`.

## 9. Обновление UI (придёт новая версия макета)

1. Положи новый `docs/UI.drawio` (если он сжат — это нормально, скрипт справляется).
2. `python tools/drawio_dump.py docs/UI.drawio -o docs/ui-dump/UI.dump.txt` и посмотри `git diff docs/ui-dump/UI.dump.txt` — это точный список изменений.
3. Обнови `docs/UI_MAP.md` (экраны, переходы, тексты, пробелы).
4. Классифицируй изменения: **только вид/текст/навигация** → правки в `:app` (Composable, строки, `UiState`-мапперы, навигация). **Изменилась логика** (новое состояние, правило, поле данных) → сначала сверься с `trackfit.md`; если там не отражено — запись в `DECISIONS.md` (тип A) и правка `:domain` + тесты + миграция БД при необходимости.
5. Один коммит `feat(app): sync UI with drawio <дата>` (+ отдельный для доменных правок, если есть).

Архитектура рассчитана на то, что смена UI затрагивает только `:app`. Если для правки макета тебе приходится лезть в `:domain` ради вёрстки — архитектура нарушена, остановись и исправь причину.

## 10. Отчётность

После каждого мержа в `develop` — короткая запись в `docs/PROGRESS.md` (дата, ветка, что сделано, что дальше). Не раздувай: 3–6 строк.
